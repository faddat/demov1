What’s powered by the SDK?+

NUNCHI SDK

Actual asset movement.

Coins: SDK genesis creates the asset and five account allocations. Signed CoinOperation::Transfer transactions run through Ledger::apply_transaction. SDK balance and nonce queries supply the readback.

Crypto + Common: public demo identities, encoding, signing and signature verification.

Oracle: signs, appends and reads a service-context record referencing the payment’s genuine SDK transaction ID.

THE APPLICATION

Requests and commerce policies.

Agent behavior, marketplace quotes, spending allocations, approved providers, approval thresholds, pauses, idempotency, service responses and the interface are application logic.

RPC, Chain, Mempool and Access Control are not used. The inspected Access Control module provides scope/role primitives; this example does not use it to enforce commerce policies.

WHY IT MATTERS

Agents need a way to pay.

A useful automated workflow may need paid data, search or compute. Developers can combine SDK transfers, signatures and records with their own services and spending rules.

The buyer can see what each job spent; a provider can trace a payment to a service request. These are application patterns demonstrated here, not an external merchant integration.

This is an in-process SDK ledger, not a complete agent wallet, merchant network, production payment gateway or audited payment service.

Simulation Assumptions & SDK Details+

Asset and accounts

SDK 2026.9.0-alpha.1, commit eea35ced709f68c15d6fbc8bcc754696a7e44374. Original Coins source is vendored unchanged and hash checked, alongside shared Crypto/Common/Oracle sources.

DCR is a disposable, two-decimal demo asset. Genesis supplies 50,000 minor units: 100 credits to each of five agents, zero to five providers. Each session derives a different asset ID. Keys are public deterministic test identities.

Execution and controls

The bridge explicitly verifies signatures before applying a Coins transaction to a cloned memory ledger. Only successful application plus matching sender/recipient readback becomes an applied payment. Failed staged state is discarded.

Application idempotency reuses an applied result by request ID. The independent SDK nonce replay test submits the original signed bytes to a disposable clone and reports the actual SDK rejection. Both are distinct.

Service fulfillment writes a related Oracle record after payment. A receipt failure leaves the payment applied and can be retried without paying again.

Limits and provenance

All services and responses are fictional. No real assets, external merchants, public-network finality, persistent QMDB, state-root proof or RPC backend are deployed. Refresh/restart clears local state.

CoinDB and OracleDB run over an app-provided memory StateStore. Browser Cargo manifests and small Common adapters disable native storage. No authenticated root or commit is claimed.

128 requests maximum. No fees configured. Context sequence/timestamps are application supplied. Export replay verifies included local evidence, not snapshot completeness or a real service outcome.
