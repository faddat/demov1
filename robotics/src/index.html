      What’s powered by the SDK?+
      WHAT NUNCHI HANDLES

      Sign. Store. Retrieve. Verify.

      Crypto & Common: the original Rust SDK signs and verifies an Oracle transaction, using its transaction encoding and demo signer keys.

      Oracle: OracleLedger applies the append, assigns the record ID and supports record, namespace and writer queries. The SDK’s database adapter reads and writes to an application-provided memory store.

      WHAT THE APPLICATION HANDLES

      The warehouse and its rules.

      Robots, paths, task scheduling, failure detection, reassignment, battery, timestamps and cost estimates belong to this application. Every reported event includes a robot, task and session identity.

      The six public demo keys represent software identities in this simulation. They do not attest to a physical device.

      WHY IT MATTERS

      A record behind the reported work.

      Applications coordinating autonomous machines can associate events with signers and tasks, retrieve the data and detect edits to signed messages.

      A valid signature establishes the integrity and signer of the message. It does not prove the reported physical action happened.

      Simulation Assumptions & SDK Details+

      The integration

      SDK release 2026.9.0-alpha.1, commit eea35ced709f68c15d6fbc8bcc754696a7e44374. Original Oracle, Common and Crypto Rust source is compiled to WebAssembly. Browser manifests disable native storage defaults. A thin Common binding provides the original namespace and state-store interfaces without a native database.

      The application calls Transaction::sign and Transaction::verify before OracleLedger::apply_transaction. The ledger does not recheck the signature itself. The application then calls records_by_namespace and record to retrieve the stored payload. Inspection runs Transaction::verify again.

      Storage is local, volatile memory. Reset and refresh clear it. Export to retain evidence. Context sequence and timestamps are application-supplied. No validator network, consensus finality, QMDB persistence, state-root proof, hardware attestation or physical safety control is provided. No RPC server is needed for this browser example.

      Illustrative operating assumptions

      Estimated cost = operating seconds × operating rate ÷ 3,600 + watt-hours ÷ 1,000 × electricity price. Moving uses 80 W; standby 12 W; charging 40 W. These are configurable application estimates, not native SDK measurements or measured robot telemetry. Failed robots stop accruing operating cost; recovery robots accrue their own. Fleet cost per delivery includes fleet standby. Battery, distance, speed and rapid charging are illustrative. Navigation is deterministic and is not a collision-avoidance or motion-planning system.

      Event windows contain 128 records to stay below Oracle’s 1,024-record bucket bound. This demo pauses at 4,096 records and asks you to export and reset. All costs use integer micro-USD in signed payloads. A new session namespace prevents reset records being confused with an earlier run.

      Keep and check the evidence

      JSON includes the original signed transaction bytes, Oracle records, payloads, robot identities and assumptions. The source project’s offline verifier replays every transaction into a fresh SDK Oracle ledger and checks signatures, nonces, identifiers and payload equality. No external price feed or network request is required.
